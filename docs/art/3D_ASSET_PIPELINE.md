# Civic Foundry 3D Asset Pipeline

This document is the operational contract for the Tranche 1 3D presentation path. It covers tracked text recipes, deterministic compilation, runtime loading, and review evidence. Generated GLB and PNG files are build outputs, not simulation or art-source authority.

## Source policy

3D source assets are tracked as human-readable JSON recipes under `assets/source/3d/`. The compiler owns the conversion from those recipes to runtime GLBs and Manifest V2 entries. Do not add generated GLBs, review PNGs, or Babylon scene state to `assets/` source directories.

House A is intentionally authored from simple deterministic primitives for the first calibration tranche. New production families may use a richer approved source workflow later, but the tracked source must still preserve the same declared dimensions, coordinate convention, materials, sockets, state channels, and LOD/collision contract.

## Coordinate contract

All dimensions and positions are in meters. Runtime geometry uses:

- `+Y` up;
- `-Z` forward/front;
- the asset origin at the ground-plane center;
- positive ground-space `X` to the right when viewed from the front.

The compiler rejects geometry below ground or outside the declared width, depth, and height envelope. Runtime placement is derived from the canonical `BuildingV2` footprint centroid and transform; no mesh node becomes a gameplay coordinate authority.

## Asset ID/naming contract

Asset IDs use a stable category/name/revision form:

```text
cf_<category>_<family>_v<two-digit revision>
```

The revision is part of the identity and is used to derive the generated file names. House A is:

```text
cf_bld_res_detached_house_a_low_v01
```

Its runtime LOD files append `_lod0.glb`, `_lod1.glb`, and `_lod2.glb`; its collision file appends `_collision.glb`.

## House A source path

```text
assets/source/3d/buildings/cf_bld_res_detached_house_a_low_v01.asset.json
```

The source declares a 9 m × 12 m × 7.6 m miniature residential cottage, the `civic-foundry-miniature` art family, parcel placement, residential/low-density compatibility, entry/service/light/tree sockets, and condition/occupancy/power/construction/night state channels.

## Compiler commands

Validate every tracked 3D recipe without writing generated outputs:

```bash
npm run assets:3d:check
```

Compile all valid recipes into `dist/`:

```bash
npm run assets:3d:build
```

The production build also compiles the 3D source as part of the complete static build:

```bash
npm run build
```

## Generated output paths

The compiler writes runtime geometry and catalogs only under `dist/`:

```text
dist/assets/models/<assetId>_lod0.glb
dist/assets/models/<assetId>_lod1.glb
dist/assets/models/<assetId>_lod2.glb
dist/assets/collisions/<assetId>_collision.glb
dist/assets/manifests/catalog-v2.json
```

House A review evidence is generated by the browser runner under:

```text
dist/assets/reviews/house-a/
```

Both generated geometry and review images are ignored build artifacts and must not be committed as source files.

## Manifest V2 contract

Each source recipe compiles to one `schemaVersion: 2` catalog entry containing:

- stable `assetId`, numeric revision, and category;
- runtime-relative LOD and collision URLs;
- dimensions and pivot metadata;
- sorted placement and socket metadata;
- material identity/family metadata;
- declared state channels;
- runtime instancing/streaming/memory hints;
- art family and quality tier.

`AssetCatalogV2` validates the generated catalog before runtime use. Runtime URLs must remain relative to the built application; absolute URLs, parent traversal, and missing files are rejected by the loading path.

## LOD/collision requirements

Every building source must provide `lod0`, `lod1`, and `lod2` entries with non-increasing triangle counts. House A currently compiles to:

```text
lod0: 300 triangles
lod1: 116 triangles
lod2: 32 triangles
collision: 12 triangles
```

Building sources must include non-empty collision geometry. The compiler validates declared bounds, ground clearance, per-LOD triangle budgets, and monotonic detail reduction before emitting files.

## Runtime loading path

The opt-in `?renderer=civic-3d` path constructs `Civic3DWorldRenderer`. Its presentation snapshot builder reads canonical `BuildingV2` records and utility/time inputs, then `Civic3DBuildingRuntime` resolves the generated catalog through `AssetCatalogV2` and streams prototypes through `AssetStreamingManager`/`BabylonGlbPrototypeLoader`.

`BuildingSceneLayer` retains presentation instances by canonical presentation ID, shares resident prototypes for matching asset/LOD keys, selects LOD from camera distance with hysteresis, and attaches pick metadata that resolves back to the canonical presentation ID. Unsupported typologies use canonical-bounds proxies; they never borrow House A geometry.

The WebGPU-first renderer uses the miniature post-processing pipeline when WebGPU is available. Chromium’s WebGL fallback uses the same lights, ground, GLB scene, camera, and state mapping with post-processing construction disabled for deterministic fallback rendering.

## Deterministic state/variation rule

The simulation remains authoritative. `WorldPresentationSnapshotBuilder` derives a presentation-only `BuildingVisualState` from canonical building lifecycle/status plus utility and visual-time inputs. Condition, power/night, vacancy, and construction update material/scaffold appearance only; they do not create or mutate simulation facts.

Variation is deterministic from the presentation identity and asset identity:

```text
visualSeed(presentationId, assetId, "base")
```

The renderer’s structural handles, Babylon nodes, materials, pipelines, and camera state are never serialized. Identical canonical input, visual time, camera state, and build outputs therefore reconstruct the same asset identity, LOD decision, and variation seed after teardown/rebuild.

## Review-camera command/output

Build the application, run the House A acceptance smoke, and generate the fixed review set:

```bash
npm run build
npm run test:smoke:3d-house
npm run review:3d-house
```

The review runner captures fixed 900 × 640 PNGs for front/rear three-quarter, top-oblique, street, neighborhood, night, worn, construction, and the named House A review scene under `dist/assets/reviews/house-a/`. It repeats the front camera capture byte-for-byte to guard deterministic review output.

## How to add the next asset family without committing binaries

1. Add one tracked JSON recipe under the appropriate `assets/source/3d/<category>/` directory with a new revisioned `assetId`.
2. Declare the coordinate/pivot, dimensions, placement compatibility, materials, sockets, state channels, runtime hints, three monotonic LODs, and collision parts.
3. Add source-contract tests for the family’s dimensions and required metadata; add runtime/presentation tests if the family introduces a new typology or state mapping.
4. Run `npm run assets:3d:check`, then `npm run assets:3d:build` and inspect the generated `dist/` outputs locally.
5. Extend the review runner only when the family has an explicit fixed-camera evidence requirement.
6. Commit the JSON recipe and tests. Leave generated GLBs and review PNGs in ignored `dist/` output; never commit those binaries to `assets/`.
